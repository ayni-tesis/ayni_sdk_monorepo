# Publicación de ayni_sdk 0.2.0 para validación técnica

**Estado:** Diseño acordado en conversación; pendiente de revisión de este documento por el usuario antes del plan de implementación.

## Propósito y resultado esperado

Publicar `ayni_sdk` 0.2.0 como la versión estable que usará la validación técnica de la tesis. La aplicación Flutter de validación se diseñará después de esta publicación. El paquete debe exponer y documentar las capacidades de observabilidad ya implementadas en `main`, resolverlas desde pub.dev en una app consumidora y conservar una correspondencia verificable entre tag, código publicado y protocolo experimental.

El usuario eligió publicar la versión estable directamente después de verificar CI. También decidió que 0.2.0 reemplace a 0.1.0 como versión evaluada y que, por ahora, se actualice solo el Plan de pruebas, sin editar OE4 ni Capstone.

## Estado comprobado el 3 de octubre de 2026

- `ayni_sdk` 0.1.0 es la versión publicada. El tag `ayni_sdk-v0.1.0` es anterior a la observabilidad del SDK.
- `main` contiene perfil técnico seguro del dispositivo, ID de instalación, trazas tipadas por ejecución, tiempos por nodo, errores sanitizados, outbox local de trazas y envío durante `sync()`. El paquete aún declara `version: 0.1.0` y su changelog no describe estos cambios.
- El servidor y el dashboard de telemetría están desplegados desde `f544458`; la política de cada aplicación permanece deshabilitada hasta que un administrador la active.
- El ejemplo Flutter resuelve `ayni_sdk: ^0.1.0`, así que sus pruebas actuales no prueban el código nuevo del paquete. La documentación de instalación también indica 0.1.0.
- El último CI de `main` verificó el SDK y los builds de Android/iOS, pero terminó en rojo por una prueba del dashboard. El release no partirá de un commit con controles requeridos en rojo.
- El Plan de pruebas v1.2 y el OE4 v1.2 fijan 0.1.0. Este diseño modifica solo una nueva copia del Plan.

## Alcance del paquete 0.2.0

La nueva versión incluye el contrato público y el comportamiento ya presentes en `main`: `DeviceProfile`, `WorkflowTrace`, `WorkflowTraceContext`, mediciones tipadas, captura local en `AyniSdk.run()`, `WorkflowResult.trace`/`WorkflowError.trace`, aviso de fallo de persistencia de la traza, `clearPendingTraces()`, restablecimiento de identidad de instalación y entrega de trazas pendientes mediante `sync()`.

La app anfitriona declara `runId`, número de repetición y los campos experimentales que conoce. La política remota debe estar habilitada y la app debe gestionar la autorización aplicable antes de pasar `traceContext`. Los campos suministrados por la app se identifican como declarados por el cliente; ni la autenticación ni el SDK certifican la equivalencia de condiciones o la calidad del instrumento. El SDK no transmite bytes de imagen, tensores arbitrarios ni la credencial dentro de la traza. La captura y el envío siguen los controles de política, reintento, acuse y retención ya implementados.

La outbox de esta versión contiene **trazas técnicas**, no resultados de captura de la aplicación. No se agregan persistencia y sincronización de resultados, selección de NNAPI/GPU, segmentación, adjuntos binarios ni cambios nuevos de inferencia. Las pruebas de esos recursos permanecen fuera del protocolo de 0.2.0. El cambio de plugin nativo y del mínimo declarado de Flutter, junto con la API pública adicional, justifican el salto de 0.1.0 a 0.2.0.

## Paquete, ejemplo y documentación

`packages/sdk_flutter/pubspec.yaml` declarará 0.2.0. `CHANGELOG.md` enumerará las capacidades publicadas y las limitaciones anteriores sin afirmar resultados de validación. El README, el ejemplo de integración y las páginas de instalación e inicio rápido documentarán el mismo contrato y la misma versión.

El ejemplo Flutter deberá resolver el SDK de este checkout durante análisis, pruebas y builds previos a publicar, para no ejercitar accidentalmente la versión 0.1.0 de pub.dev ni depender de un 0.2.0 aún inexistente. Una dependencia local relativa en el ejemplo es la opción prevista, sujeta a que `dart pub publish --dry-run` valide el archivo publicable. Después de publicar se verificará por separado que una app consumidora pueda resolver `ayni_sdk: ^0.2.0` desde pub.dev.

La referencia Dart generada se regenerará con la versión de Flutter fijada por CI (3.44.8) y se comprobará que el sitio de documentación describa solo funciones efectivamente publicadas. Las referencias históricas explícitas a 0.1.0 se actualizarán cuando indiquen la versión vigente; no se reescribirán hechos históricos.

## Verificación y publicación

Antes de crear el tag se verificará el archivo de publicación con `dart pub publish --dry-run`, análisis y pruebas del paquete y del ejemplo, referencia Dart, documentación, y builds de consumidores Android e iOS con la configuración soportada. Se investigará el fallo de CI general del dashboard y se corregirá si es reproducible; un reintento verde solo bastará si la evidencia muestra que el fallo fue transitorio. El commit exacto de publicación deberá tener en verde los controles requeridos de `main`.

El tag nuevo e inmutable será `ayni_sdk-v0.2.0` y apuntará al commit verificado. El flujo existente `.github/workflows/publish-sdk.yml` comprobará que tag, `pubspec.yaml` y entrada no vacía de changelog coincidan, ejecutará sus builds y publicará mediante la configuración actual de pub.dev. No se reutilizará ni moverá el tag 0.1.0. Tras el flujo, se comprobarán la página y API de pub.dev, la versión y la resolución de la dependencia hospedada. Si la publicación falla, primero se comprobará si 0.2.0 ya llegó a pub.dev; un fallo transitorio podrá reintentarse sobre el mismo tag, mientras que un cambio de código exigirá una nueva versión y un nuevo tag, sin mover el anterior. No se afirmará que 0.2.0 está disponible hasta comprobarlo.

La publicación en pub.dev es permanente. Antes de crear o empujar el tag se mostrará al usuario el diff, el commit y el resultado de las verificaciones para revisión final.

## Actualización del Plan de pruebas

La fuente será el Plan v1.2 del 2 de octubre, no el v1.1 adjuntado inicialmente. Se crearán copias v1.3 en Markdown y DOCX junto a los originales y se mantendrá el contenido de ambos formatos alineado. La versión evaluada pasará a `ayni_sdk` 0.2.0 con su tag y commit verificados. Esta actualización ocurrirá después de comprobar la publicación, para no nombrar como disponible una versión todavía no publicada.

El Plan distinguirá evidencia del SDK, contexto declarado por la app y mediciones externas. `runId`, repetición, `traceId`, versión de workflow y modelo, resultado tipado, duraciones, error, estado de persistencia y acuse del servidor se vincularán al instrumento por corrida. Se describirán la política desactivada por defecto, la autorización de captura en la app, la retención configurada, la copia de evidencia antes del vencimiento y la comprobación de que no se envían imágenes, entradas crudas, tensores ni secretos. SEC-01 y los escenarios offline pertinentes incorporarán comprobaciones de encolado, reintento y acuse de **trazas**; no adoptarán el criterio de cero pérdidas/duplicados para **resultados** que 0.2.0 no almacena.

El Plan conservará los umbrales ya aprobados como hipótesis previas a la medición. No se completarán firmas, datos pendientes de congelar ni tablas de resultados por inferencia. El documento indicará que OE4 y Capstone siguen describiendo 0.1.0 y requieren alineación posterior, sin modificarlos en este trabajo.

## Criterios de término y siguiente etapa

Esta etapa termina cuando 0.2.0 aparece en pub.dev, la dependencia hospedada se resuelve en una app consumidora, el tag coincide con el código y las verificaciones, y el Plan v1.3 refleja con precisión el contrato publicado sin inventar mediciones. El diseño de la app de validación, sus dos integraciones equivalentes y la preparación de imágenes/modelos/workflows constituyen la siguiente etapa.
