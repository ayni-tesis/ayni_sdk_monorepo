# Ayni SDK 0.2.0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Publish `ayni_sdk` 0.2.0 with the observability already implemented on `main`, verify a hosted consumer, and update only the versioned technical test Plan to use this release.

**Architecture:** The Flutter package and its example are verified from the same checkout before the release exists on pub.dev. The existing tag-triggered GitHub workflow publishes the verified commit; a separate hosted-package check confirms the artifact users install. The thesis Plan is versioned after publication and distinguishes trace delivery from application-result persistence.

**Tech Stack:** Dart/Flutter 3.44.8 in CI, GitHub Actions, pub.dev, Bun/Astro documentation, Markdown, DOCX.

**Spec:** [Ayni SDK 0.2.0 release design](../specs/2026-10-03-ayni-sdk-0.2.0-release-design.md)

## Global Constraints

- Package version and tag: `0.2.0` and `ayni_sdk-v0.2.0`; never move the existing `ayni_sdk-v0.1.0` tag.
- Keep the package's declared floors: Dart `>=3.8.0 <4.0.0`, Flutter `>=3.32.0`, Android API 26+, iOS 11.0+.
- Publish only the SDK observability and device-profile behavior already implemented in `main`; no result outbox, backend selection, segmentation, binary attachments, or new inference behavior.
- Telemetry defaults off. A host app passes `traceContext` only with the applicable permission; input images, tensors, credentials, and direct hardware identifiers never enter traces.
- The publication workflow, full branch CI, Android and iOS consumer builds, package archive check, and hosted dependency check must pass before calling the release complete.
- The Plan v1.2 dated 2026-10-02 is the academic source. Produce Plan v1.3 in Markdown and DOCX alongside it; do not edit OE4 or Capstone, invent measurements, fill signatures, or change approved thresholds.
- Local Windows `flutter doctor` is currently blocked by Application Control and `adb`/Java/Android SDK are not visible in the usual paths. CI may verify the release; record local verification limits without treating them as passing tests.

## Review Focus

- A consumer might accidentally resolve published 0.1.0 while the release is prepared; Task 1 checks the example's dependency source and resolved version.
- The publish archive might omit new plugin files or contain unwanted local state; Task 1 checks `dart pub publish --dry-run` and the included-file list.
- A disabled, missing, or revoked policy must not create or send a trace; Task 3 runs the existing policy, outbox, and SDK tests covering these cases.
- The failing dashboard test may be a real regression or a transient failure; Task 3 isolates it and requires a full green CI result on the release commit.
- A green tag workflow alone might leave pub.dev without the package or a consumer unable to resolve it; Task 4 checks the pub.dev version and a fresh hosted dependency resolution.
